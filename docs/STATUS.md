## 真机（11-16 到货，已跑通）

设备插在电脑上是 COM3（乐鑫芯片自带的 USB 串口，不用装驱动）。芯片 ESP32-S3（QFN56，v0.2），16 MB 闪存，8 MB PSRAM，MAC 10:20:ba:6d:5e:c0。

出厂备份：

- `backup/`（不进仓库）：整片 16 MB 闪存，读的时候芯片停在下载模式，是完整快照；读完在芯片上逐区校验，除 NVS（出厂系统开机后会重写）外全部一致。`backup/parts/` 是按分区切开的，`backup/README.md` 写了怎么刷回出厂。
- NVS 里有出厂系统存的 Wi-Fi（`Xiaomi_7F24`）、设备 uuid、官方云令牌、PHY 校准。我们的固件不擦 NVS，直接用这里的 Wi-Fi。

固件（`firmware/`，ESP-IDF v5.5.4，LVGL 9.5.0 和仿真器同版本、同配置）：

- 编译：WSL 里 `bash firmware/build.sh`（把源码同步到 `~/work/codetalky` 再编，结果放 `firmware/out/`，不进仓库）。烧录：Windows 里 `.\firmware\flash.ps1`（只写引导、分区表、OTA 选择和 ota_0，NVS 和官方的数据分区不动）。看日志：`uv run --no-project --with pyserial python -I tools/esp/serial_log.py COM3 20`（`--reset` 先重启；USB 口复位时会断开一下，开机最早那段日志可能看不到，用 `esptool chip_id` 复位后马上开日志能看到大部分）。
- 分区表和出厂一样，随时能把官方固件刷回 ota_0。
- `board.c`：上电先拉高总电源和屏幕供电（扩展 IO TCA9555），复位触摸，震动马达，电量计（BQ27220，按电压折算，和官方一样）。充电芯片 CX25601N 还没接管，沿用出厂固件设好的寄存器（电池不断电就一直有效）；以后做电源策略时要移植它的初始化和后台任务。
- `ssd1677.c`：屏幕驱动，初始化顺序和波形表照官方，不用“RAM 乒乓”，每次刷新前两个平面都显式写。
- `epd.c`：LVGL 画 RGB565，按仿真器的规则转成灰度级，比对后只在有变化时刷；刷屏在单独任务里，界面和触摸不等它。两遍：先黑白（非白即黑），停 0.45 秒后灰度叠加（把字边的黑像素推浅）。已经是灰的像素在之后的局刷里按“白到白”下发，波形不碰它们，否则局刷的“保持黑”脉冲会把灰压回黑。
- `input.c`：每 10 毫秒读一次触摸（CST816S，坐标就是竖屏 480×800）和按键，按下、松开都锁存，LVGL 忙时点击也不丢。屏幕下方三个触摸键报固定坐标（y=900，x=80/240/400 → 主页/下一页/上一页）。电源键按住 3 秒关机，开机时还按着的那一下不算。
- `net.c`：连出厂存的 Wi-Fi（开机约 1 秒）；UDP 广播找电脑（8137 到 8140 端口），每台电脑一条 WebSocket，按 hostId 固定编号；电脑正常关闭连接后也重连，断开超过 10 秒又收到这台电脑的应答就重建连接。
- `hal.c`：NVS 键名超过 15 个字符的（`key:<电脑编号>`）用哈希映射。

电脑端改动：

- 默认在 `0.0.0.0` 上监听（以前是 127.0.0.1），同时开 UDP 发现（`bridge/src/discovery.ts`，同端口号），设备自己找到电脑，不用填 IP。钩子入口仍只接受本机。仿真器地址打印成 127.0.0.1。
- 配对实测通过：设备上显示码，电脑上确认，设备上点“配好了”；之后重启、重烧固件都不用再配（密钥在 NVS 里）。

真屏实测（室温）：

- 刷新耗时：局刷 560 毫秒，快刷（整屏闪一下）1018 毫秒，全刷（屏自带波形）1021 毫秒（数据手册写 3.2 秒，实际快得多），灰度叠加 143 毫秒。仿真器参数已改成这些。
- 文字：50% 阈值的纯黑白太细，看不清；非白即黑清楚但锯齿；加灰度叠加后好看；你又要求加粗一档，现在是浅灰边按深灰显示、深灰边按黑显示（`epd.c` 的 `TEXT_WEIGHT`，仿真器同步）。你说“先这样，后续再微调”。字号仍是 20，你觉得偏小，但先不动。

## 第 7 项：接 Claude Code 钩子（已完成）

真的 Claude Code 会话现在会出现在设备上，能在设备上批准、拒绝、回答它的提问。

怎么用：

```sh
cd bridge
node src/main.ts hooks --merge ~/.claude/settings.json   # 加钩子，旧文件留 .codetalky.bak
node src/main.ts --fake                                  # 起服务（--fake 可省）
node src/main.ts hooks --remove ~/.claude/settings.json  # 不用了就撤掉
```

钩子是 Claude Code 自带的 HTTP 钩子，发到 `http://127.0.0.1:8137/hooks/claude`。只有 SessionStart 例外：Claude Code 规定它只能是命令型钩子，所以用转发脚本 `bridge/hooks/hook.mjs`（和 Codex 共用）。服务没开时 Claude Code 照常工作，钩子连不上不会拦它。我没有改你的 `~/.claude/settings.json`，要不要加由你决定。

怎么工作的（`bridge/src/claude/`）：

- 一个 Claude Code 会话对应设备上一行，名字是项目文件夹名；模型名和 git 分支从会话记录里读，读不到就显示“—”。
- 你每发一条指令开始新的一轮：计数、改动文件、改动片段清零；活动记录保留。
- 每一步工具调用记一条：读了多少行、搜到几处、改了几行（用 Claude Code 自己的补丁，改动片段带真实行号）、命令完成或失败。待办列表来自它的 TodoWrite。
- 完成汇报用它最后一段回复，Markdown 的要点、加粗开头会变成汇报里的圆点和粗体。
- 批准请求：设备连着时，钩子等设备回话，期限默认 570 秒（`--hold` 可改）。交互式 Claude Code（2.1.323 实测）在钩子等待的同时，终端里也照常弹确认框，两边谁先答算谁的：
  - 设备先答，终端的确认框自己消失，接着干活；
  - 终端先答，Claude Code 挂断钩子请求，设备马上离开批准页，显示“已在电脑上处理”（万一没挂断，看到这个工具的结果也会离开）；
  - 期限到了、设备断了、或者根本没设备连着，钩子不给结论，终端的确认框还在，照常在电脑上答。
- 改文件的请求在设备上显示要改的行，会去文件里找出第几行；命令显示整条，理由用命令自带的说明。删除、推送、强推、`reset --hard` 这类命令要长按批准。
- 同时来的几个请求排队，一个一个显示。
- 它用 AskUserQuestion 提问时，在设备上点选项回答；一次问几道题就依次显示。
- 一次性运行（`claude -p`）一结束会话就关了，汇报会留着，你点“知道了”才移走；正常退出的会话直接移走；12 小时没动静的会话也会清掉。
- 普通终端里开的会话不能从设备发新指令（设备上显示“只能查看”），要等“托管终端”。

实测过（用最便宜的 haiku 模型，在临时目录里跑，三次一共约 0.01 美元）：

- `claude -p` 让它跑一条命令：设备上出现等批准，点批准后命令真的执行了。
- `claude -p` 让它改一个文件：设备上看到要改的行，批准后改动片段和 Claude Code 的补丁一致，完成汇报的要点正确。
- 交互式 Claude Code（用 pywinpty 开的伪终端）让它用 AskUserQuestion 提问：设备上点了选项，终端里显示收到了答案，它的回复里说的就是这个选项。`claude -p` 模式里没有 AskUserQuestion，只能这样测。
- 11-13 托管终端整套（`codetalky claude --model haiku --permission-mode default`，测试脚本同时扮演设备和坐在终端前的人，终端画面用 xterm 无头终端截下来）：
  - 启动 3 秒设备上就出现会话，能发指令；中文指令打进输入框并提交了。
  - 第 1 个批准在设备上点：155 毫秒后 Claude Code 继续。
  - 它正忙时设备发第 2 条指令：Claude Code 排进队里，做完手上这步就接着做。

## 配对（已完成）

局域网里的设备要先配对才能连电脑，本机连接（仿真器）不用。设备第一次连某台电脑时提示配对：你在那台电脑上运行 `codetalky pair`，设备上出现 6 位配对码，输入它，再在设备上点“配好了”，以后自动认证。

- 只有能操作那台电脑的人才能配对；配对前设备发的动作一律不算。
- （11-14 外部审核后）配对码只在你运行 `codetalky pair` 开的 5 分钟窗口里出现，每个窗口最多 3 次，重连、换编号都不退：原来中间人能反复开新交换去撞同一个码（审核复现约 31 万次撞上）。新配对两边都要确认（电脑上输入码，设备上点“配好了”）。电脑说“不认这把密钥”时设备不再自己删密钥，而是问你要不要重新配对（这条消息谁都能伪造）。没认证的连接 6 分钟内没完成就断开，同时最多 8 个。图在 `ui-22`（等你开窗口）、`ui-18`（设备确认）、`ui-23`（配好了）、`ui-24`（电脑不认了）。
- （11-14 加强）配对码不再是设备随便抽的数，而是设备和电脑各自从配对交换里算出来的（X25519 加“先承诺后揭晓”，同蓝牙的数字比对）。有人在中间偷换密钥，两边的码就对不上，你在电脑上输入设备上的码就配不上。双方的共同密钥各自算出，从不在网上传；以后每次连接电脑出随机挑战，设备证明自己有这把密钥，然后整条连接用 ChaCha20-Poly1305 加密，冒充、篡改、重放、偷看都不行。细节见 `docs/PROTOCOL.md` 的“配对”。
- 设备端用 Monocypher 4.0.2（`third_party/monocypher/`，公有领域授权，官网和 GitHub 两处下载的哈希一致），电脑端用 Node 自带的加密。用编译好的设备代码（仿真器的 WebAssembly）和电脑端实际跑过：配对、存密钥、断线重连后用密钥证明、从设备加密批准，都通过；两边算出的配对码一致。
- 电脑把配对密钥存在 `~/.codetalky/devices.json`（文件权限只给本用户）；`codetalky devices` 列出，`codetalky unpair` 撤销，撤销后设备下次连会被拒并重新要求配对。以前用令牌配对的设备要重配一次（还没有真机，影响不到什么）。
- 同时最多 3 个配对请求在等（多了直接拒绝），同一个码对上两个请求就都不配：免得同网段的人塞进成千上万个请求，碰巧占住你要输入的码。电脑在任何地方都不打印配对码。
- 配对码 5 分钟有效，设备快到时重新打招呼换新码；点“以后再说”不再弹出，列表里留着提示。
- 加 `--require-pairing` 可以在仿真器里试配对界面；截图工具用 `--pair`/`--pair-wait`、`--open`、`--approve`（像用户一样读设备上的码去电脑上输入）、`--relink`、`--unpair`。图在 `design/renders/ui-17`、`ui-18`、`ui-22` 到 `ui-24`。
- 硬件接口加了持久存储、随机数（必须是密码学强度的：真机用开着无线的 esp_random）和断开连接（`ct_hal_net_close`）。设备默认只认配对过、加密的连接（`CT_REQUIRE_SECURE` 默认为 1，只有仿真器编译成 0）；NVS 的键名最长 15 个字符，`key:<电脑编号>` 要在固件里映射一下。
- 已知局限：电脑上的 `devices.json` 里是明文密钥，拿到这个文件就能冒充设备（和 SSH 私钥一样，靠文件权限保护）。
- `--insecure-lan` 还在，意思是“局域网设备跳过配对”，只供调试；真机默认连不上这种电脑。
